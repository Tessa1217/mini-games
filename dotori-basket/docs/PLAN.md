## 1. 컨셉

동물의 숲 무드(파스텔·둥근 형태·따뜻한 조명)의 캐주얼 낙하물 받기 게임.
머리 위에 바구니를 얹은 **다람쥐**를 레인 사이로 옮기며, 떨어지는 **과일**을 **레시피 순서대로** 받는다.

핵심 스킬은 반사신경이 아니라 **"오답을 피해 정답 레인까지 가는 경로와 타이밍 판단"** 이다.

## 2. 레인 구조

```
 ┌────┬────┬────┬────┬────┐
 │ L0 │ L1 │ L2 │ L3 │ L4 │
 │ 🍎 │    │ 🍊 │    │    │   ← 레인별 독립 낙하, 시작 시점 제각각
 │    │    │    │ 🍓 │    │
 │    │ 🍇 │    │    │    │
 ├╌╌╌╌┼╌╌╌╌┼╌╌╌╌┼╌╌╌╌┼╌╌╌╌┤   ← 바구니 라인 (판정선)
 │         🐿️(L2)          │
 └─────────────────────────┘
   [ ◀ ]              [ ▶ ]
```

### 2-1. ⭐ 불변식: 시각 위치 === 논리 위치 (위치 보간 금지)

게임 로직에서 다람쥐의 위치는 `laneIndex: 0..4` **정수 하나**이고,
**화면상 위치도 항상 그 레인에 정확히 있다.** 레인 간 위치를 부드럽게 보간하지 않는다.
이동 연출은 **제자리 기울기/스쿼시**(`snapTiltMs`)로만 준다.

> **왜 보간하면 안 되는가** — 위치를 `laneTransitionMs`로 glide시키면, 그 값이 홀드 리피트
> 간격과 같거나 클 때 **스프라이트가 레인 N에 도착하는 순간 로직은 이미 N−1로 넘어가 있다.**
> 홀드 연속 이동 내내 시각과 판정이 **상시 1레인(72px = 화면 폭의 20%)** 어긋나고,
> "눈에는 바구니가 과일 밑에 있는데 놓침 판정"이 난다.
> 밸런스 수치로는 못 고치는 구조 결함이라 **불변식으로 못 박는다.**

- 판정·상태가 완전히 결정적이라 디버깅과 테스트가 쉽다
- 연속 좌표의 "반쯤 걸친 상태" 같은 애매한 판정이 원천적으로 없다
- 시각 피드백과 판정이 절대 어긋나지 않는다

**이동해도 경로 판단은 사라지지 않는다.** 이동 1회마다 `moveCooldownMs`(120ms)가 걸리므로
4칸을 가려면 최소 360ms 동안 **중간 레인들을 순차 점유**한다. 그 사이 중간 레인에 오답이
떨어지면 맞는다. "언제 출발할지 / 돌아갈지 / 기다릴지"의 판단이 그대로 유지된다.

⚠️ 즉시 스냅이 최고 속도(120ms 간격)에서 끊겨 보일 수 있다. 기울기·스쿼시 연출이
그걸 흡수하지 못하면, 보간을 되살리는 대신 **`moveCooldownMs`를 올리는 쪽**으로 대응한다
(보간 부활은 위 불변식 위반).

### 2-2. 이동 — 단일 게이트

**모든 입력이 `moveCooldownMs`(120ms) 하나를 통과한다.** 탭·홀드·키보드가 같은 게이트다.

> **왜 단일 게이트인가** — 홀드에만 리피트 간격을 걸면, 인간 연타(70~100ms/회)가 홀드보다
> 항상 빨라진다. 그러면 난이도를 결정하는 노브가 **최적 플레이에서 무력화**되고,
> "4칸 이동에 시간이 걸리므로 경로 판단이 생긴다"는 설계 전제가 통째로 무너진다.

- **탭 1회 = 1레인** (쿨다운 중 입력은 **1개까지만 버퍼링** — 무한 큐잉이 아니다)
- **홀드 = auto-repeat, A안(표준 키 리피트)**: 누르는 즉시 1회 이동 → `holdInitialDelayMs`(250ms)
  대기 → 이후 `holdRepeatMs`(120ms) 주기
- 거리 d레인 소요시간: **최속(연타) = (d−1) × `moveCooldownMs`** / 홀드 = `250 + (d−2) × 120`
  → 4칸 기준 최속 360ms, 홀드 490ms
- 양 끝에서 정지 (wrap-around 없음)

### 2-3. 획득 판정 — 라인 통과 이벤트

과일이 **바구니 라인(y 임계값)을 통과하는 순간**, 그 시점의 다람쥐 레인과 과일 레인을 비교한다.

```
과일이 라인을 넘는 프레임에 1회만 평가:
  fruit.lane === squirrel.lane  →  획득 (정답 판정으로)
  아니면                        →  통과 (놓침, 페널티 없음)
```

연속 겹침(overlap) 검사가 아니라 **크로싱 이벤트**인 것이 중요하다.
- 과일은 아래로만 움직이므로 라인을 정확히 **한 번** 넘는다 → 중복 판정 불가능
- 겹침 검사였다면 생겼을 "라인에 걸쳐 있는 동안 들락날락하며 판정이 여러 번" 문제가 없다
- 스윕 판정·터널링 처리가 불필요해진다 (프레임 간 y를 비교하면 끝)

바구니의 시각적 크기는 연출일 뿐, 판정은 **레인 인덱스 일치** 하나다.

> ⚠️ **크로싱 이벤트가 막지 못하는 것**: 통과 **직전** 프레임에 그 레인으로 이동해서 받는 것은
> 막지 않는다(막을 이유도 없다 — 아슬아슬하게 끼워 넣는 조작이 이 게임의 재미다).
> 다만 `moveCooldownMs`(§2-2)가 없으면 연타로 임의의 레인에 즉시 끼어들 수 있어
> "타이밍을 잰다"가 "아무 때나 눌러도 된다"로 바뀐다 — 쿨다운이 그 게이트다.

## 3. 스포너 규칙

레인 구조에서는 스포너가 **플레이 가능성을 보장**해야 한다.

| 규칙 | 내용 | 없으면 |
|---|---|---|
| **레인 최소 간격** | 같은 레인의 직전 과일이 일정 거리 내려가기 전엔 다음 과일 금지 | 한 레인에 과일이 붙어 판정이 뭉갬 |
| **정답 기아 방지** | 최근 M초간 현재 타깃 과일이 스폰되지 않았으면 다음 스폰을 강제로 정답으로 | 레시피가 진행 불가 |
| **동시 통과 상한** | 아래 3-1 | 피할 수 없는 배치 |
| **정답 도달 가능성** | 정답 스폰 시 `(거리 − 1) × moveCooldownMs < 낙하 잔여시간` (최속 기준) | 봐도 못 받는 정답 |

**규칙 충돌 시 우선순위** (`spawner.rulePriority`):
`crossLimit > laneGap > starvation > reachability`
기아 강제 스폰이 다른 규칙을 만족하는 레인을 못 찾으면 **스폰을 1틱 미루고 기아 타이머는 계속
진행**한다 — 규칙을 어기지 않는다.

> ⚠️ **도달 가능성 검사는 현재 수치에서 거의 발동하지 않는다** (최속 4칸 360ms vs 최소 낙하시간
> 1.364s). 이건 잘못된 config를 잡는 **싼 assertion**으로 남겨두는 것이고, 실제로 정답을 못 받는
> 주된 원인인 "**가는 길에 오답이 있다**"는 이 검사가 측정하지 않는다 — 그건 불공정이 아니라
> **이 게임의 핵심 난이도**이므로 의도적으로 막지 않는다.

### 3-1. ⭐ 밀도 제약은 "화면 존재 수"가 아니라 "동시 통과 수"다

난이도를 올리려고 스폰 밀도를 높이면 회피 공간과 정면으로 충돌한다 —
5레인에서 동시에 4개가 떨어지면 빈 레인이 1개뿐이고, 그게 멀면 못 간다.

하지만 **화면에 몇 개가 떠 있는지는 사실 제약이 아니다.** 문제가 되는 건
*같은 시간대에 바구니 라인을 통과하는 과일 수*뿐이다. 시차만 있으면 화면에 5개가 있어도
순서대로 피하면 된다.

그래서 제약을 이렇게 정의한다.

```
통과 시각 윈도우(±0.4초) 안에 라인을 통과하는 과일 수 ≤ 3   (= 레인 5 − 회피용 2)
```

스폰 시점에 그 과일의 **예상 통과 시각**을 계산해 윈도우 내 카운트를 확인하고,
초과하면 스폰을 미루거나 다른 레인으로 돌린다.

→ 이렇게 하면 **화면 밀도(체감 난이도)는 계속 올리면서 회피 가능성은 보장**된다.

### 3-2. ⭐ 밀도는 `spawnIntervalSec`이 만든다 — `maxOnScreen`이 아니다

화면 동시 존재 수는 캡으로 만드는 게 아니라 **케이던스로 결정된다**:

```
밀도 ≈ 낙하시간 / 스폰간격,   낙하시간 = catchLineY / (baseFallSpeed × fallSpeedMultiplier)
```

**낙하 속도와 스폰 간격을 같은 비율로 줄이면 밀도가 제자리걸음이 된다.**
그래서 `spawnIntervalSec`을 **속도보다 빠르게** 줄인다. 결과: 밀도 Lv1 2.00 → Lv7 3.99 → Lv19 4.70.

`maxOnScreen`은 **난이도 축이 아니라 안전 상한**이다. 자연 밀도보다 넉넉히 위에 두어 지터가
누적된 이상 구간만 잡는다. **자연 밀도보다 낮게 잡으면 스폰 간격 설정을 무력화**하므로 주의.

### 3-3. ⭐ 스폰 지터가 없으면 §3-1의 상한은 죽은 가드다

케이던스가 완전히 균일하면 크로싱도 균일하게 배치되어, 윈도우(0.8s) 안에 들어갈 수 있는
크로싱 수가 `floor(0.8 / 간격) + 1`로 고정된다. 간격이 0.4s보다 크면 **상한 3에 구조적으로
도달할 수 없다** — 가드가 한 번도 발동하지 않는다.

그래서 스폰 간격에 무작위 편차를 준다: `실제 간격 = spawnIntervalSec × (1 ± spawnJitterRatio)`.
`spawnJitterRatio = 0.35`에서 **Lv6부터 상한이 실제 가드로 발동**한다(§14에서 실행 검증).
리듬이 기계적으로 들리지 않게 하는 효과도 겸한다.

### 3-4. 스폰 케이던스는 전역이다

`spawnIntervalSec`은 **레인별이 아니라 전체에서 이 주기로 1개**를 뜻한다.
레인은 위 규칙을 만족하는 후보 중에서 고른다. (레인별로 해석하면 밀도가 5배가 된다.)

### 3-5. 오답 비율 — 카테고리 추첨 순서를 명문화

스폰 시 "현재 타깃 과일"을 뽑을 확률(`correctSpawnRatio`)을 레벨마다 낮춘다 → 오답 밀도 상승.
단 **정답 기아 방지 규칙이 하한선** 역할을 하므로 진행 불가로 빠지지 않는다.

카테고리는 **1회 다항 추첨**으로 정한다 — 순차 추첨을 하면 방해물 노브가 정답 비중 노브를
침식해서 "방해물률을 올렸더니 레시피 진행이 느려졌다"의 원인을 못 찾게 된다.

```
P(방해물) = obstacleDropRate
P(정답)   = correctSpawnRatio
P(오답)   = 1 − 위 둘의 합          ← 합이 1을 넘으면 정규화하지 말고 assert
```
(현재 최대치는 Lv13+ 기준 0.22 + 0.20 = 0.42로 안전)
오답 풀에는 **현재 타깃을 제외**한 해금 과일만 넣는다.

## 4. 게임 규칙

### 4-1. 레시피 큐

HUD 상단에 `🍓 → 🍎 → 🍊`. 맨 앞이 현재 타깃(하이라이트 + 펄스).
받으면 체크 → 다음. 전부 채우면 완성 보너스 → 새 레시피.
생성 시 현재 해금된 과일 중에서만 뽑고, 같은 과일이 연속 2회 이상 나오지 않게 한다.

### 4-2. 판정 3종

| 상황 | 결과 |
|---|---|
| **정답** 획득 | +점수 × 콤보배율, 레시피 1칸 진행 |
| **오답** 획득 | **HP −1**, 콤보 리셋, 0.8초 무적, 과일 튕겨나가며 소멸. **레시피 진행·타이머는 유지** |
| **놓침** | **페널티 없음** (콤보도 유지). 노브: `hp.missPenaltyHp`, 기본 0 |

설계 원칙: **개별 실수는 용서하고, 전체 정체만 처벌한다.**
동시 낙하 구조에서 "오답을 피하느라 정답을 못 받는" 건 정상 플레이의 일부이므로 놓침은 무페널티로 두고,
대신 아래 레시피 타이머가 전역 압박을 담당한다.

### 4-3. ⭐ 레시피 제한시간

**목적 두 가지**
1. 아무것도 안 받고 버티는 플레이 차단 (빈 레인으로 회피만 하는 경우 포함)
2. 놓침 무페널티로 느슨해진 긴장감 회복

**규칙**
- 새 레시피 생성 시 타이머 시작, HUD에 게이지 바로 표시
- 만료 시 → **HP −1 + 레시피 재생성 + 콤보 리셋** (확정)
- 오답을 받아도 타이머는 리셋되지 않음 (레시피 진행이 유지되므로 일관)
- 레벨업 배너·일시정지 동안에는 타이머 정지
- 잔여 25% 또는 4초 이하에서 **경고 상태** (게이지 적색 + 펄스)

**시간 배분** ⚠️
```
제한시간 = 레시피 길이 × 항목당 시간
항목당 시간: Lv1 8.0s → 레벨마다 −0.3s → 하한 5.0s
예) Lv1(길이2) 16.0s · Lv4(길이3) 21.3s · Lv7(길이5) **31.0s**
```
정상 플레이에서는 거의 걸리지 않고, **의도적으로 안 받을 때만** 걸리는 수준으로 잡는다.
타이머가 상시 압박이 되면 "피하는 판단"이라는 이 게임의 핵심이 죽는다.

### 4-4. HP

- 시작 **3** (도토리 3개) ⚠️
- 오답 1회 = −1, 피격 후 **0.8초 무적** (깜빡임으로 표시)
- **레벨업 회복 없음** (`healOnLevelUp: 0`) — 아래 참조
- 0 → Game Over (낙하 중 과일 페이드아웃)

**무적의 범위 (명문화)**: 데미지만 무효다.
- 무적 중에도 **정답 획득은 정상 동작** (밀집 구간에서 억울한 손실 방지)
- 추가 오답은 소멸하되 데미지 0
- 단 **무적 중에는 콤보가 오르지 않는다** — 일부러 오답을 먹고 0.8초 무적으로 밀집 구간을
  관통하는 전략을 막기 위함 (고레벨 낙하시간이 1.364s라 0.8초는 통과 윈도우 하나를 통째로 덮는다)

**레벨업 HP 회복을 두지 않는 이유**: 난이도 축이 전부 상한에 걸리는 레벨을 계산하면
방해물 Lv13 · 정답비중 Lv14 · 스폰간격 Lv18 · 속도 Lv19로, **Lv19 이후 난이도가 완전히 정적**이다.
종료 조건이 HP 소진뿐인데 레시피 3개마다 HP가 회복되면 숙련자 세션이 **원리적으로 끝나지 않는다.**
"HP가 다 닳으면 game over"라는 실패 모델을 유지하려면 회복이 없어야 한다.

### 4-5. 점수

```
정답 획득   : 10 × combo_multiplier
레시피 완성 : 50 × 레시피 길이
콤보 배율   : 1 + floor(연속정답 / 5) × 0.5   (상한 3.0)
```
최고 점수는 `localStorage` — **접근 자체가 throw할 수 있으므로 try/catch 필수** (시크릿 모드).

### 4-6. 레벨 / 난이도 테이블 ⚠️ (초안, 플레이테스트로 조정)

| Lv | 해금 과일(누적) | 종류 | 레시피 | **정답 비중** | **스폰 간격** | → 밀도 | 안전상한 | **방해물** | 낙하 속도 |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 🍓 🍎 | 2 | 2 | 55% | 1.50s | 2.00 | 4 | — | 1.00 |
| 2 | + 🍊 | 3 | 2 | 50% | 1.19s | 2.29 | 5 | — | 1.10 |
| 3 | + 🍐 | 4 | 3 | 45% | 0.96s | 2.60 | 5 | — | 1.20 |
| 4 | + 🍇 | 5 | 3 | 40% | 0.80s | 2.88 | 5 | 5% | 1.30 |
| 5 | + 🍑 | 6 | 4 | 36% | 0.67s | 3.20 | 6 | 8% | 1.40 |
| 6 | + 🍋 | 7 | 4 | 32% | 0.56s | 3.57 | 6 | 11% | 1.50 |
| 7 | + 🍉 | 8 | 5 | 29% | 0.47s | 3.99 | 7 | 14% | 1.60 |
| 8+ | — | 8 | 5 | −1%/lv (≥22%) | −0.015s/lv (≥0.28s) | →4.87 | 8 | +1%/lv (≤20%) | +0.05/lv (≤2.2) |

- **밀도 컬럼은 파생값**이다(낙하시간 ÷ 스폰 간격). 직접 설정하는 값이 아니라 결과다.
- **안전 상한은 난이도 축이 아니다**(§3-2). 전 레벨에서 자연 밀도보다 위에 있음을 §14에서 검증.
- **동시 통과 상한 3은 전 레벨 고정** (§3-1) — 지터 덕에 Lv6부터 실제 가드로 발동
- 레벨업 조건: **레시피 3개 완성마다 +1** ⚠️
  — "완성"은 **레시피의 모든 항목을 획득한 경우**만 뜻한다.
  타이머 만료로 인한 재생성은 완성에 포함되지 않는다(포함하면 버티기 플레이가 레벨업한다).
- 해금 연출: 중앙 배너 "새로운 과일! 🍇" + 짧은 정지 (인지할 시간 확보)
- 모든 수치는 `game/config/balance.ts` 한 곳에 — 코드 수정 없이 튜닝

### 4-7. 방해물

**구현 비용이 거의 0이다.** 방해물 = *레시피에 절대 등장하지 않는 아이템*이므로,
과일 정의에 플래그 하나만 추가하면 기존 판정 로직을 그대로 탄다.

```ts
{ id: 'acorn_rotten', neverInRecipe: true, ... }   // 받으면 항상 오답 → HP −1
```

필요한 건 **아트뿐**이라 Phase 1에 포함한다.

**확정: 돌멩이 🪨 · 나뭇가지 🪵 2종.**
벌레·썩은 과일은 시각적 불쾌감이 있어 제외했다 — 동물의 숲 무드와도 맞지 않는다.
돌멩이·나뭇가지는 "먹을 수 없는 것"이 한눈에 읽히면서 화면이 징그러워지지 않는다.
과일과 확실히 구분되도록 **각진 실루엣 · 낮은 채도**로 잡는다.

> 별도 효과를 가진 방해물(화면 가림, 좌우 반전, 일시 감속)은 규칙이 달라지므로 **Phase 2**.

## 5. 입력

| 액션 | 데스크탑 | 모바일·웹뷰 |
|---|---|---|
| 좌/우 1레인 | `←` `→` / `A` `D` (홀드 repeat) | 하단 **좌/우 버튼** (탭 + 홀드 repeat) |
| 일시정지 | `Esc` | 우상단 버튼 |
| 시작/재시작 | `Enter` `Space` | 버튼 탭 |

버튼은 **최소 56×56px**, 하단 코너(엄지 도달 범위), `env(safe-area-inset-bottom)` 반영.

### 5-1. 홀드 구현 주의

`onClick`으로 만들면 홀드 연타가 안 된다. `onPointerDown`에서 repeat 타이머 시작,
**`onPointerUp` · `onPointerCancel` · `onPointerLeave` 셋 다**에서 정지.
**`pointercancel`/`leave`를 빠뜨리면 손가락이 버튼 밖으로 미끄러졌을 때 다람쥐가 계속 달린다** — 웹뷰에서 특히 자주 나는 버그.
`setPointerCapture`로 포인터를 버튼에 고정하는 편이 안전하다.

### 5-2. ⭐ 키보드 입력 규칙 (웹 + 웹뷰 공통)

포인터 홀드의 함정(§5-1)에는 **키보드 판박이가 그대로 존재**한다. 다섯 가지를 명시한다.

| 항목 | 규칙 | 안 지키면 |
|---|---|---|
| **OS 키 리피트** | `event.repeat === true`인 `keydown`은 **무시**하고, 반복은 자체 게이트(`moveCooldownMs`)로만 낸다 | OS 리피트(~30ms)가 쿨다운을 무시해 데스크탑에서 난이도 노브가 무력화 |
| **키 식별** | `event.key`가 아니라 **`event.code`**(`KeyA`/`KeyD`/`ArrowLeft`/`ArrowRight`) | 한글 입력 상태에서 `event.key`가 `'ㅁ'`/`'ㅇ'`을 반환해 A/D가 죽는다 |
| **키 상태 유실** | `blur` · `visibilitychange`에서 **눌린 키 상태 전체를 리셋** | 키를 누른 채 앱이 전환되면 `keyup`이 안 와서 다람쥐가 계속 달린다 (§5-1의 `pointercancel` 문제와 동일) |
| **기본 동작** | 게임이 쓰는 키에 `preventDefault()` | 방향키로 페이지가 스크롤된다 |
| **포커스 충돌** | 게임 단축키는 `document` 레벨에서 처리하되 **포커스가 버튼에 있으면 무시**(또는 `pointerup`에서 `blur()`) | §5-3이 좌/우를 실제 `<button>`으로 만들므로, 게임오버 후 Space가 **포커스된 방향 버튼을 클릭**한다 |

> 인앱 웹뷰에는 하드웨어 키보드가 없는 것이 기본이지만 **블루투스 키보드 연결은 가능**하다.
> 위 규칙은 웹·웹뷰 양쪽에 동일하게 적용한다.

### 5-3. 추상화

`useGameInput`은 **의도만** 내보낸다: `{ moveDir: -1 | 0 | 1, pause: boolean }`.
게임 로직은 키보드인지 터치인지 모른다.

### 5-4. 접근성

- 좌/우는 **실제 `<button>`** (div + onClick 금지)
- 과일은 **색만으로 구분하지 않음** — 실루엣을 충분히 다르게
- `prefers-reduced-motion` → 파티클·흔들림 축소

## 6. 기술 스택

| 항목 | 선택 | 비고 |
|---|---|---|
| 프레임워크 | Next.js (App Router) | 게임은 단일 클라이언트 컴포넌트, SSR 불필요 |
| 빌드 | **`output: 'export'`** | 웹뷰에 정적 번들 통째로 투입 가능 (Next 이미지 최적화는 비활성) |
| 언어 | TypeScript | 과일 id·상태를 유니온 타입으로 고정 |
| 애니메이션 | framer-motion (v12+ 패키지명 `motion`) | **연출 전용** — §6-1 |
| 렌더 | DOM + CSS transform | 레인 구조라 DOM이 잘 맞음. 동시 오브젝트 ~10개면 Canvas 불필요 |
| 테스트 | Vitest | 순수 로직(판정·레시피·스포너·레벨) |

### 6-1. ⭐ framer-motion의 역할 한계

**낙하 자체를 framer-motion으로 애니메이션하면 안 된다.**
`animate={{ y: 800 }}`로 떨어뜨리면 매 프레임 y를 알 수 없어 **라인 통과 판정이 불가능**하고,
일시정지·속도 변경을 중간에 다루기 어려우며, 애니메이션 값과 게임 상태가 **두 곳으로 갈라진다.**

| 영역 | 수단 |
|---|---|
| **낙하·이동·판정** (매 프레임 연속값) | 자체 루프 — RAF + 고정 타임스텝, `ref.style.transform` 직접 갱신 |
| **이산 연출** (상태 전환 시 1회) | framer-motion — 획득 팝, 오답 튕김, HP shake, 레벨업 배너, 오버레이 전환(`AnimatePresence`) |

framer-motion은 **"상태가 바뀌는 순간의 연출"** 을 맡는다. 무드의 대부분이 거기서 나온다.

> ⭐ **불변식: 같은 노드에 두 주체가 쓰지 않는다.**
> 역할을 나눠도 함정이 남는다 — 획득 팝·오답 튕김의 대상은 **낙하 중이던 바로 그 과일 노드**라,
> RAF가 매 프레임 쓰는 `transform`을 framer-motion이 동시에 관리하게 된다.
> 게다가 과일 노드는 **오브젝트 풀링으로 재사용**되므로, 퇴장 연출이 도는 중에 풀로 반환되면
> 새 과일이 이전 과일의 튕김 애니메이션을 이어받는다.
>
> **해결**: 판정 즉시 과일 노드를 풀로 반환하고, 연출은 **별도 이펙트 레이어의 일회용 노드**에서
> 재생한다(이펙트 풀에서 꺼내 framer-motion으로 재생 후 반환). 낙하 노드와 연출 노드를 분리하면
> 두 주체가 같은 엘리먼트를 만질 일이 없다.

### 6-2. ⭐ React 성능 원칙 — 60fps로 변하는 값은 state에 두지 않는다

과일 y를 `useState`에 넣고 매 프레임 `setState`하면 초당 60회 × N개 리렌더로 모바일 웹뷰에서 바로 무너진다.

```
게임 상태(과일 배열·y·다람쥐 레인) → useRef 기반 mutable store
                                      RAF에서 직접 변경 + DOM ref에 transform 쓰기 (리렌더 0)

HUD(점수·HP·레벨·레시피·타이머)     → useState (저빈도)
                                      시스템이 이벤트 emit → 구독해서 갱신
```
과일 DOM 노드는 **오브젝트 풀링**으로 재사용 (생성/삭제 반복 시 GC 스파이크가 모바일에서 체감됨).
타이머 게이지는 매 프레임 갱신이므로 **state가 아니라 CSS 변수/transform으로** 처리한다.

### 6-3. 게임 루프

**고정 타임스텝(1/60) + accumulator + 렌더 보간.**
기기·프레임레이트가 달라도 동일한 난이도. `dt`는 `min(dt, 1/30)`으로 clamp —
탭 복귀 시 dt가 수 초로 튀어 과일이 라인을 건너뛰는 버그를 막는다.

⭐ **이동 쿨다운·auto-repeat는 벽시계(`setTimeout`/`setInterval`)가 아니라 루프의 누적 시간으로
구동한다.** DOM 이벤트는 `heldDir`만 갱신하고, 실제 이동 판정은 고정 스텝 안에서 한다.
- `setInterval`로 돌리면 **일시정지·레벨업 배너(§9) 동안에도 리피트가 계속 발화**해서,
  배너가 끝나는 순간 다람쥐가 엉뚱한 레인에 있다
- 입력 반영 시점이 프레임과 무관해져 결정성이 깨진다

**레벨업 시 속도 변화는 신규 스폰부터 적용**한다. 비행 중인 과일의 속도를 바꾸면
§3-1이 스폰 시점에 계산해둔 "예상 통과 시각" 장부가 전부 무효가 된다.

### 6-4. 좌표계

논리 좌표(예: 360×640)로 계산하고 컨테이너에 `scale`만 적용.
레인 폭 = `논리폭 / 5`. 해상도 대응이 한 곳에 격리되어 밸런싱 수치가 기기마다 흔들리지 않는다.

## 8. 웹뷰 대응 (`platform/`) — 지금 넣어둘 것

"나중에 웹뷰"를 전제로, **지금은 거의 공짜인데 나중에 붙이면 레이아웃·입력을 전면 수정해야 하는 것**만 선반영한다.

**⭐ 정적 번들 로딩 스킴 (지금 정해야 하는 결정)**
Next의 `output: 'export'`는 기본적으로 `/_next/static/…` **절대경로**를 생성한다.
호스트 앱이 `file://`로 로드하면 **전 자산이 404**다. 셋 중 하나를 택한다:
- (a) `assetPrefix: './'` 로 상대경로 생성 *(가장 간단)*
- (b) iOS `WKURLSchemeHandler` / Android `WebViewAssetLoader` 로 커스텀 스킴 제공
- (c) 앱 내 로컬 http 서버

"지금은 공짜, 나중에 붙이면 전면 수정"이라는 이 절의 선별 기준에 정확히 해당하므로 선반영한다.

**viewport**
- `100vh` 금지 → `100dvh` + `env(safe-area-inset-*)` (iOS 주소창·노치·홈 인디케이터)
- `<meta viewport>`에 `viewport-fit=cover`
- ⚠️ **`user-scalable=no`는 확대를 막는 수단이 아니다** — iOS Safari는 접근성 정책상 이를 무시한다.
  실제로 막는 것은 `touch-action: none` + 더블탭/`gesturestart` 차단이다. meta는 보조일 뿐,
  "이걸로 된다"고 믿으면 실기기에서 원인을 엉뚱한 데서 찾게 된다.
- 세로 고정: **웹뷰에서는 네이티브 호스트가 방향을 고정하는 것이 정답**이다
  (아래 `NativeBridge.lockOrientation`). Android Chrome은 fullscreen 진입 후
  `screen.orientation.lock('portrait')`도 동작한다.
  **안내 오버레이는 웹 단독 실행 시의 폴백**이지 유일한 수단이 아니다.

**제스처 차단**
- `touch-action: none`, `overscroll-behavior: none`
- `touchmove`를 **non-passive**로 `preventDefault()` — iOS 바운스
- `user-select: none`, `-webkit-tap-highlight-color: transparent`, `-webkit-touch-callout: none`
  — 버튼 홀드 조작이라 **반드시 필요** (길게 누르면 선택·컨텍스트 메뉴가 뜬다)

**생명주기**
- `visibilitychange` / `pagehide` → **자동 일시정지** (앱 전환·전화 수신)
- 복귀 시 dt clamp (§6-3)
- 리스너·RAF·타이머에 teardown 경로 — 웹뷰는 SPA 내 재진입이 잦다

**브릿지 스텁 (`bridge.ts`)** — 인터페이스만 정의, no-op 구현
```ts
interface NativeBridge {
  isAvailable(): boolean
  /** 세로 고정 — 웹뷰에서 방향을 실제로 강제할 수 있는 유일한 경로 */
  lockOrientation(orientation: 'portrait'): void
  haptic(type: 'light' | 'error'): void
  shareScore(score: number): void
  close(): void
}
```
런타임에 `window.webkit?.messageHandlers`(iOS) / `window.AndroidBridge`(Android)를 **기능 감지**해서
있으면 호출, 없으면 no-op. 웹 개발 중엔 영향 0, 탑재 시점에 구현만 채우면 된다.
햅틱 웹 폴백은 `navigator.vibrate` (iOS 미지원 → 기능 감지 필수).

## 10. 아트 방향

파스텔, 채도 낮은 초록·크림·우드, 둥근 실루엣, 굵은 아웃라인 없음.
다람쥐는 대기/이동/피격/환호. 배경은 숲 레이어 2~3장 아주 느린 패럴랙스.

**과일은 실루엣만으로 구분 가능해야 한다** — 8종까지 늘어나는데다 색각 이상 대응도 겸한다.
방해물은 과일과 확실히 다른 실루엣(각진 형태·어두운 톤)으로 즉시 구분되게.

**초기엔 도형·이모지 플레이스홀더로 로직부터 완성한다.** 렌더 레이어를 분리해두면
에셋 대기 때문에 로직 개발이 막히지 않는다.

## 12. 밸런싱 방침

수치는 **지금 확정하지 않는다.** 낙하 속도·타이머·오답 비율 같은 값은 숫자만 보고는
감이 잡히지 않고, 실제로 플레이해봐야 판단할 수 있는 영역이다.

대신 **튜닝 표면(인터페이스)을 먼저 열어두고** P3~P4에서 플레이하며 조정한다.
시스템 코드에는 리터럴을 절대 남기지 않는다 — 모든 수치는 `balance.ts`를 거친다.

## 13. 튜닝 인터페이스 (작성 완료)

플레이테스트에서 직접 만질 수 있도록 타입과 설정 파일을 미리 만들어뒀다.
**TypeScript strict 타입체크 통과 + 경계값 실행 검증 완료.**
(레포에 `tsconfig.json`이 아직 없어 외부 tsc로 검증했다 — P0에서 tsconfig 추가 시 CI로 편입할 것)

| 파일 | 역할 |
|---|---|
| `game/types.ts` | 모든 설정의 타입 정의. 각 필드에 "무엇을 조절하는 값인지" 주석 |
| `game/config/items.ts` | 과일 8종 + 방해물 2종. 해금 레벨·무게·플레이스홀더 |
| `game/config/balance.ts` | **★ 밸런싱 단일 지점** — 모든 수치가 여기 하나에 |
| `game/config/levels.ts` | 레벨 → 난이도 변환. 8레벨 이후 무한 외삽, 레시피 제한시간 계산 |

### 13-1. 조절 가능한 것

```
lane        레인 수 · 논리 좌표계 · 판정선 y
movement    moveCooldownMs ← 경로 판단 난이도를 좌우 · 홀드 초기딜레이/리피트 · 기울기 연출 길이
hp          최대 HP · 무적 시간 · 레벨업 회복량(0) · 놓침 페널티(0)
scoring     기본 점수 · 완성 보너스 · 콤보 단계/증가량/상한
recipe      제한시간 배분 · 경고 시점 · 만료 페널티 · 연속 중복 금지 구간
spawner     동시 통과 상한 · 통과 윈도우 · 스폰 지터 · 레인 간격(px) · 기아 방지
            · 도달 가능성 · 기준 낙하속도 · 규칙 우선순위
levelUp     레벨업 조건 · 배너 시간
levels[]    레벨별: 레시피 길이 · 정답 비중 · **스폰 간격(밀도)** · 안전 상한 · 방해물률 · 속도
endless     8레벨 이후 레벨당 증감량과 상·하한
```

### 13-2. 설계상 의미가 큰 노브 3개

- **`movement.moveCooldownMs` (120ms)** — 탭·홀드·키보드 **공통 게이트**.
  최속 4칸 이동 = 3 × 이 값 = 360ms. 이 게임의 핵심인 "경로 판단" 난이도를 이 값이 결정한다.
  줄이면 회피가 쉬워져 단순 받기 게임에 가까워지고, 늘리면 판단 비중이 커진다.
  ⚠️ 홀드 리피트에만 걸면 탭 연타(70~100ms)로 우회되므로 **반드시 공통 게이트**여야 한다.
- **`levels[].spawnIntervalSec`** — 체감 밀도를 만드는 **유일한** 실질 노브(§3-2).
  `maxOnScreen`은 안전 상한일 뿐 밀도를 만들지 않는다.
  낙하 속도와 **같은 비율로 줄이면 밀도가 제자리걸음**이 되므로 항상 속도보다 빠르게 줄인다.
- **`spawner.spawnJitterRatio` (0.35)** — 0으로 두면 케이던스가 완전히 균일해져
  `simultaneousCrossLimit`이 **구조적으로 도달 불가능한 죽은 가드**가 된다(§3-3).
- **`recipe.expirePenaltyHp` (1)** — 0으로 두면 "레시피 재생성만" 동작으로 바뀐다.
  버티기 차단이 과하다고 판단되면 여기만 0으로 내린다.

### 13-3. 규칙

- 새 수치가 생기면 **반드시 `balance.ts`에 추가**하고 시스템 코드엔 리터럴을 남기지 않는다
- 시스템 코드는 `BALANCE.levels`를 직접 읽지 않고 항상 `tuningForLevel(level)`을 호출한다
  (8레벨 이후 외삽이 한 곳에만 존재하도록)
- 에셋이 나오면 `items.ts`의 `color`/`placeholder`를 sprite 경로로 교체하고 렌더 레이어만 바꾼다
- 수치를 바꾼 뒤에는 **P4.5 시뮬레이터로 규칙 발동 횟수를 확인**한다 — 어떤 규칙의 발동이 0이면
  그 노브는 죽어 있다는 뜻이다(rev.4에서 실제로 3건 발생)

### 14-2. 실행 검증 결과 (rev.5 수치)

설정값을 실제로 로드해 계산한 결과다. 표의 밀도는 추정이 아니라 **실측**이다.

**Lv2로 폴백**한다.

### 14-5. 난이도 재조율 (2026-09-15 · rev.6)

질문지 10문항에 대한 답을 받아 반영했다. 답은 전부 A안이었다.

| | 결정 | 이전 → 이후 |
|---|---|---|
| Q1 | 레벨당 1~2분 · 제한시간 10초대 | 레벨당 22초 → 슬라이더로 조정 중 |
| Q2 | 반응 속도형 | 밀도 2.00→3.98 → **2.99→3.94** (Lv1부터 바쁘게) |
| Q3 | Lv1에 과일 4종 | 2종 → **4종** |
| Q4 | 길이 3부터 | 2·2·3·3·4·4·5 → **3·3·4·4·5·5·6** |
| Q5 | 순서 위반 = HP −1 | 변경 없음 |
| Q6 | 여유 일정하게 | 고정 상수 → **slack에서 역산** |
| Q7 | 놓침 = 콤보 리셋 | `missResetsCombo: true` 추가 |
| Q8 | 방해물 Lv3 | Lv4 → **Lv3** |
| Q9 | HP 3 · 회복 없음 | 변경 없음 |
| Q10 | 3개마다 ×0.5 · 최대 ×2.5 | 5개마다 ×0.5 · 최대 ×3.0 |

**Q3이 핵심이었다.** "Lv1이 너무 간단하다"의 원인은 레시피 길이가 아니라 **풀 크기**였다.
Lv1에 과일이 2종뿐이라 `noRepeatWindow: 1`까지 걸리면 나올 수 있는 레시피가
`사과→귤` / `귤→사과` **두 가지뿐**이었다. 여기서 길이만 3으로 늘려도 `사과→귤→사과` 꼴로
고정되어 가짓수는 그대로다. 4종으로 늘리자 **36가지**가 됐다.

**제한시간을 역산식으로 바꿨다.** rev.5는 `길이 × 항목당 시간`이라는 고정식이라, 스폰을
빠르게 바꾸면 타이머만 혼자 헐거워졌다 — 실제로 여유가 Lv1 +7.6초에서 Lv7 +21.0초로
**벌어져** 압박 곡선이 거꾸로였다. 이제는:

```
정답간격 = spawnIntervalSec ÷ correctSpawnRatio
낙하시간 = catchLineY ÷ (baseFallSpeed × fallSpeedMultiplier)
최소소요 = recipeLength × 정답간격 + 낙하시간
제한시간 = max(minSec, 최소소요 + slackSec)
```

스폰을 어떻게 바꿔도 체감 압박이 따라온다.

#### ⚠️ slackSec이 아직 틀렸다 — 회피 비용이 빠져 있다

`slackSec: 3.0`으로 두고 봇을 돌리자 **3판 전부 Lv1에서 12~31초 만에 죽었고,
사망 원인 6건 중 4건이 시간초과**였다.

원인은 최소소요 계산에 **회피 비용이 없다**는 것이다. 위 식은 "정답이 오면 항상 받는다"를
전제하는데, 실제로는 오답을 피하느라 정답을 그냥 보내게 된다. 한 번 보낼 때마다
정답간격(Lv1 기준 1.43초)이 통째로 날아가므로, **두 번만 놓치면 여유 3.0초가 증발한다.**

즉 slack은 "몇 초를 더 준다"가 아니라 **"정답을 몇 번 지나쳐도 되는가"**로 읽어야 하고,
값은 정답간격의 배수여야 한다.

**slack 스윕 (레벨당 8레시피 · 여유별 3판 · 봇 플레이)**

```
여유    Lv1 제한   평균 생존   평균 점수   시간초과 사망   오답 사망
+3s      10.3s       15초        33          3            3
+5s      12.3s       25초        93          3            3
+7s      14.3s       36초       388          0            6   ← 전환점
+9s      16.3s       23초       190          1            5
```

**+7초에서 시간초과 사망이 0이 된다.** 그 지점부터 사인이 전부 "오답을 받아서"로 바뀐다 —
타이머가 범인이 아니라 실력이 한계가 되는 지점이고, 설계 의도(§4 "타이머는 회피 플레이만
차단한다")와 맞는 상태다. 정답간격 1.43초 기준 **+7초 ≈ 정답 4.9번을 지나칠 여유**다.

⚠️ 판당 3회뿐이라 **+7과 +9는 통계적으로 구분되지 않는다.** +9가 더 나빠 보이는 것은 편차다.

#### 그래도 "10초대"가 안 된다 — 이건 산수 문제다

+7초면 Lv1 제한이 14.3초다. 3개짜리 레시피에서 **마지막 하나가 판정선까지 내려오는 3.0초**만으로
10초 예산의 3분의 1이 나간다. 제한을 10초대로 두면서 시간초과 사망을 0으로 유지하려면
타이머를 조이는 게 아니라 **게임 전체가 빨라져야** 한다 — 낙하가 빠르면 같은 시간에
더 많은 기회가 지나가기 때문이다. Q2 «반응 속도» 선택과 방향이 같다.

**낙하 ×1.5 검증 결과** — 같은 여유(정답 4.9회)에서 제한이 14.3초 → 13.3초. 방향은 맞지만
1초밖에 안 줄었다. 최소소요 `길이×정답간격 + 낙하시간`에서 낙하를 빠르게 한 건 **뒤쪽 항만**
건드리고, 앞쪽 `3×1.43=4.3초`는 그대로이기 때문이다. **정답간격도 같이 줄여야** 한다.

#### 해법 — 기준 낙하 속도를 올리고 스폰 간격을 당긴다

여유 5회를 유지한 채 제한 10초를 만드는 조건을 역산했다:
`(3+5)×정답간격 + 낙하 = 10`, 낙하 2.0초 → **정답간격 1.00초** (기존 1.43초).

- `baseFallSpeedPxPerSec` **167 → 250** (500px 낙하 3.0초 → 2.0초)

#### rev.7 — 난이도 축을 '개수'에서 '속도'로 (2026-09-15)

플레이 피드백 두 가지를 받았다.

1. **제한시간 때문에 어이없이 지는 판이 있다** — 낙하가 랜덤이라 정답이 한동안 안 나오면
   실력과 무관하게 진다.
2. **개수가 늘어도 레벨업이 어려워진 느낌이 없다.**

둘은 같은 뿌리다. **레인이 5개라 화면에 몇 개가 더 떠도 피할 자리가 남는다** — 밀도는
난이도로 잘 바뀌지 않는다. 그래서 밀도를 올려 난이도를 만들려던 설계 자체가 헛돌았고,
그 와중에 역산 제한시간(«최소소요 + 여유»)만 스폰 난수에 그대로 노출돼 있었다.

**제한시간을 30초 고정으로 바꿨다.** 최소소요가 5.4~6.3초이므로 약 5배 여유다 —
정상 플레이에서는 걸리지 않고, §4 원래 의도대로 **안 받고 버티는 회피 플레이만** 막는다.
난수가 패배를 결정하는 경로가 사라진다.

**난이도는 낙하 속도가 전담한다.** 밀도는 2.80으로 고정하고 속도만 크게 올렸다.
체감을 만드는 값은 **«끝에서 끝까지 피하고 남는 시간»** = 낙하시간 − 4칸 × `moveCooldownMs`다.

```
Lv 길이 속도  낙하   간격  밀도 정답률 최소소요 제한 회피여유 0.8s창 방해물
 1   3  ×1.00 2.50s 0.890 2.81  70%   6.31s  30s   2.02s  0.90   0%
 3   4  ×1.46 1.71s 0.610 2.81  58%   5.92s  30s   1.23s  1.31   6%
 5   5  ×2.00 1.25s 0.450 2.78  49%   5.84s  30s   0.77s  1.78  12%
 7   6  ×2.63 0.95s 0.340 2.80  42%   5.81s  30s   0.47s  2.35  18%
19   6  ×3.83 0.65s 0.270 2.42  30%   6.05s  30s   0.17s  2.96  26%
```

회피여유 2.02초 → 0.47초. 이전 표(rev.6)는 Lv7 낙하가 1.30초였으므로 **37% 빨라졌다.**

- `fallSpeedMax: 3.85` (낙하 0.65초) — 4칸 이동 0.48초 + 반응 시간에 겨우 남는 수준이 상한이다.
- `0.8s창`이 3 미만이므로 `simultaneousCrossLimit`이 스폰을 막지 않는다. Lv19에서 2.96으로
  경계에 닿는다 — 이보다 간격을 더 줄이면 스포너가 throttle한다.
- Lv8 이후 밀도가 2.80 → 2.42로 내려가는 것은 의도된 결과다. 간격이 하한(0.267초)에 묶인 채
  낙하만 빨라지기 때문이고, **개수가 아니라 속도가 축**이므로 문제가 되지 않는다.

계기판에 `낙하` · `회피여유`를 띄워 튜닝 중에 바로 보이게 했다.

#### 화면 흐름 추가 (2026-09-15)

`로딩 → 타이틀 ⇄ 놀이법 → 게임 ⇄ 해금 카드 → 게임 오버` 를 `PHASE` 상태 기계로 붙였다.

**해금 카드는 게임을 멈춘다.** 과일이 떨어지는 중에 알림을 띄우면 읽을 수가 없다.
2.2초 자동 해제 + 탭/Enter로 즉시 재개. 방해물은 «조심하세요»로 과일과 분리해 보여준다 —
받으면 도토리가 깎이는 것들이라 "새로 나왔어요" 목록에 섞으면 안 된다.

해금이 없는 레벨(Lv6·Lv7·무한)은 멈추지 않고 배너만 띄우며, 문구는 그 레벨에서 실제로
바뀐 것(레시피 길이 / 방해물 / 속도)을 말한다.

**일시정지** — HUD 버튼 + `Esc`/`P` 토글. `PHASE='paused'`로 `step()`을 막고, 재개할 때
`last`·`acc`를 리셋해 멈춘 시간만큼 낙하가 점프하지 않게 한다(실측: 0.9초 정지 후 재개
직후 진행 6.7px = 정상 1프레임분).
**`document.hidden`이면 자동으로 멈춘다** — 웹뷰에서 앱을 전환했다 돌아왔을 때 그 사이
판이 진행돼 있으면 안 된다(§8 웹뷰 항목).

**화면 오버레이 배경** — 로딩·타이틀·놀이법은 가운데까지 나무가 이어지는 숲길을 쓴다
(`bg-forest-full.jpg`). 게임 배경은 낙하 경로를 비워야 해서 좌우에만 나무가 있는데,
떨어지는 것이 없는 화면에서까지 가운데가 빈 하늘이면 이질적이다.
**생성 없이 기존 배경에서 조립했다** — 왼쪽 나무가 줄기 바로 오른쪽에서 잘려 있어
x=0 미러링으로 온전한 나무가 복원된다는 점을 이용했다. 절차는 `prototype/README.md`에 적었다.

**작업 중 만들었다가 고친 버그 1건** — `caught()`에서 `newRecipe()`를 `checkLevelUp()`보다
먼저 호출해, 레벨업 직전의 새 레시피가 **옛 레벨 기준(길이·제한시간)으로 생성**되고 있었다.
순서를 되돌렸다. 레벨업까지 손으로 갈 수 없어 `?dbg` URL 파라미터로 테스트 훅
(`__dbg.jump(lv)` · `state()` · `start()`)을 열어 확인했다.

#### ⚠️ 여기서부터는 봇으로 검증할 수 없다

낙하 2.0초 빌드에서 봇은 11초 만에 죽었다. **100ms 폴링 봇에게는 회피 판단에 3틱밖에
없기** 때문이다(2.5초로 되돌린 뒤에도 사람보다 불리한 건 같다). 사람보다 현저히 불리한 조건이라, 이 숫자에 맞춰 더
조정하면 봇에 과적합된다. **`slackCorrectGaps` · `recipesPerLevel` · 실패 시 진행도 리셋
세 가지는 사람 플레이로 확정해야 하며, 프로토타입 튜닝 패널에 슬라이더/토글로 열어 두었다.**

### 14-6. ⚠️ 아직 검증되지 않은 것

- **Lv4 이상 미검증** — 방해물(돌멩이·나뭇가지)은 Lv4부터, 수박·배·체리는 Lv5~7부터 등장한다.
  봇이 Lv3까지만 도달해 **해당 구간은 코드 경로만 있고 실측이 없다**.
- **Lv8 이후 무한 구간 미검증** — 아트가 8종에서 멈추므로 프로토타입 풀은 Lv7에서 고정된다.
  `items.ts`의 레몬 이후 8종은 그림이 없다.
- **framer-motion 경합**(§6)은 여전히 설계 추론이다. 프로토타입은 순수 RAF + CSS transform으로만
  돌았고 framer-motion을 쓰지 않았다.
- **실기기 미검증** — §8 웹뷰 항목은 공개 스펙 기반이다. 대상 앱의 웹뷰 설정(`WKWebView` pinch
  처리, `WebViewAssetLoader` 사용 여부 등)에 따라 달라질 수 있다.
- **게임성 수치**(점수 10/50, 콤보 ×3.0, 시작 HP 3, 즉시 스냅의 체감)는 플레이 없이 판단 불가다.
- `docs/DESIGN.md`는 아직 없다 — 아트·UI 결정은 다음 단계.

# 레인 구조와 이동

## 2. 레인 구조

```
 ┌────┬────┬────┬────┬────┐
 │ L0 │ L1 │ L2 │ L3 │ L4 │
 │ 🍎 │    │ 🍊 │    │    │   ← 레인별 독립 낙하, 시작 시점 제각각
 │    │    │    │ 🍓 │    │
 │    │ 🍇 │    │    │    │
 ├╌╌╌╌┼╌╌╌╌┼╌╌╌╌┼╌╌╌╌┼╌╌╌╌┤   ← 바구니 라인 (판정선)
 │         🐿️(L2)          │
 └─────────────────────────┘
   [ ◀ ]              [ ▶ ]
```

### 2-1. ⭐ 불변식: 시각 위치 === 논리 위치 (위치 보간 금지)

게임 로직에서 다람쥐의 위치는 `laneIndex: 0..4` **정수 하나**이고,
**화면상 위치도 항상 그 레인에 정확히 있다.** 레인 간 위치를 부드럽게 보간하지 않는다.
이동 연출은 **제자리 기울기/스쿼시**(`snapTiltMs`)로만 준다.

> **왜 보간하면 안 되는가** — 위치를 `laneTransitionMs`로 glide시키면, 그 값이 홀드 리피트
> 간격과 같거나 클 때 **스프라이트가 레인 N에 도착하는 순간 로직은 이미 N−1로 넘어가 있다.**
> 홀드 연속 이동 내내 시각과 판정이 **상시 1레인(72px = 화면 폭의 20%)** 어긋나고,
> "눈에는 바구니가 과일 밑에 있는데 놓침 판정"이 난다.
> 밸런스 수치로는 못 고치는 구조 결함이라 **불변식으로 못 박는다.**

- 판정·상태가 완전히 결정적이라 디버깅과 테스트가 쉽다
- 연속 좌표의 "반쯤 걸친 상태" 같은 애매한 판정이 원천적으로 없다
- 시각 피드백과 판정이 절대 어긋나지 않는다

**이동해도 경로 판단은 사라지지 않는다.** 이동 1회마다 `moveCooldownMs`(120ms)가 걸리므로
4칸을 가려면 최소 360ms 동안 **중간 레인들을 순차 점유**한다. 그 사이 중간 레인에 오답이
떨어지면 맞는다. "언제 출발할지 / 돌아갈지 / 기다릴지"의 판단이 그대로 유지된다.

⚠️ 즉시 스냅이 최고 속도(120ms 간격)에서 끊겨 보일 수 있다. 기울기·스쿼시 연출이
그걸 흡수하지 못하면, 보간을 되살리는 대신 **`moveCooldownMs`를 올리는 쪽**으로 대응한다
(보간 부활은 위 불변식 위반).

### 2-2. 이동 — 단일 게이트

**모든 입력이 `moveCooldownMs`(120ms) 하나를 통과한다.** 탭·홀드·키보드가 같은 게이트다.

> **왜 단일 게이트인가** — 홀드에만 리피트 간격을 걸면, 인간 연타(70~100ms/회)가 홀드보다
> 항상 빨라진다. 그러면 난이도를 결정하는 노브가 **최적 플레이에서 무력화**되고,
> "4칸 이동에 시간이 걸리므로 경로 판단이 생긴다"는 설계 전제가 통째로 무너진다.

- **탭 1회 = 1레인** (쿨다운 중 입력은 **1개까지만 버퍼링** — 무한 큐잉이 아니다)
- **홀드 = auto-repeat, A안(표준 키 리피트)**: 누르는 즉시 1회 이동 → `holdInitialDelayMs`(250ms)
  대기 → 이후 `holdRepeatMs`(120ms) 주기
- 거리 d레인 소요시간: **최속(연타) = (d−1) × `moveCooldownMs`** / 홀드 = `250 + (d−2) × 120`
  → 4칸 기준 최속 360ms, 홀드 490ms
- 양 끝에서 정지 (wrap-around 없음)

### 2-3. 획득 판정 — 라인 통과 이벤트

과일이 **바구니 라인(y 임계값)을 통과하는 순간**, 그 시점의 다람쥐 레인과 과일 레인을 비교한다.

```
과일이 라인을 넘는 프레임에 1회만 평가:
  fruit.lane === squirrel.lane  →  획득 (정답 판정으로)
  아니면                        →  통과 (놓침, 페널티 없음)
```

연속 겹침(overlap) 검사가 아니라 **크로싱 이벤트**인 것이 중요하다.
- 과일은 아래로만 움직이므로 라인을 정확히 **한 번** 넘는다 → 중복 판정 불가능
- 겹침 검사였다면 생겼을 "라인에 걸쳐 있는 동안 들락날락하며 판정이 여러 번" 문제가 없다
- 스윕 판정·터널링 처리가 불필요해진다 (프레임 간 y를 비교하면 끝)

바구니의 시각적 크기는 연출일 뿐, 판정은 **레인 인덱스 일치** 하나다.

> ⚠️ **크로싱 이벤트가 막지 못하는 것**: 통과 **직전** 프레임에 그 레인으로 이동해서 받는 것은
> 막지 않는다(막을 이유도 없다 — 아슬아슬하게 끼워 넣는 조작이 이 게임의 재미다).
> 다만 `moveCooldownMs`(`rules/lane.md`)가 없으면 연타로 임의의 레인에 즉시 끼어들 수 있어
> "타이밍을 잰다"가 "아무 때나 눌러도 된다"로 바뀐다 — 쿨다운이 그 게이트다.
